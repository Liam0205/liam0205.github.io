把 item 压成 KV：gist 压缩的成本与边界

发表于 2026 年 10 月 30 日 分类于 Algorithm and Computer Science 阅读次数：
本文字数： 6.2k 阅读时长 ≈ 11 分钟

搜索相关性模型的输入正被推着往长里走，标题、属性、详情这些字段被拼在一起，一条 item 动辄上千 token；与此同时，同一批 item 一天之内要被不同的 query 反复打分许多次。把这两件事叠在一起看，很自然会浮出一个想法：既然被复用的是 item，那么不妨在离线阶段就把它压成一小段 KV 存起来，在线只让 query 对着这段 KV 做注意力，从而把 j 从在线计算里整个拿掉。

这个想法在论文里有个干净的形式，叫 gisting（《Learning to Compress Prompts with Gist Tokens》，Jesse Mu、Xiang Lisa Li、Noah Goodman，NeurIPS 2023，arXiv:2304.08467）。但那套形式是为平均 26 个 token 的指令设计的，无论输入分布、压缩比还是任务性质，都与我们这里差着一大截，所以成本得全面重算。此篇把这项成本拆开算一遍；算完会发现三件不太一样的事：算力上的收益被高估了，存储上的收益被模型配置吃掉一半，而真正决定成败的地方，在这两者之外。

初步讨论

为什么要压缩

相关性打分的成本几乎全在 prefill。一条 item 的 j 个 token 加上一条 query 的 ℓ 个 token，配 N 条候选，就是 j + ℓ 跑 N 遍；由于 j 通常在一千上下而 ℓ 只有几十，这 N 遍里有九成以上的算力花在重复读同一段 item 上。

自然想到缓存 item 的前缀（prefix cache），命中就省掉重算。这是 HuggingFace 里现成的一行配置，也是 vLLM 默认给人的能力。问题在于缓存本身的大小。每个位置的 KV 是 2 × 层数 × KV 头数 × head_dim 个数；以 24 层、2 个 KV 头、head_dim 64、d = 896 为例，一个位置 12 KiB，一条 1000 token 的 item 光前缀就要 12 MiB，10 万条就是 1.2 TB。缓存还没换成吞吐，先把显存吃干净了。

gist 换掉的是「哪段文本产生这些 KV」这件事：不再存 j 个 token 的 KV，而是让 item 自己读出 k 个位置，把这 k 个位置的 KV 存下来。同一份信息，12 MiB 压到 96 KiB，128 倍。它没有发明新机制，只是把「留多少 token 给后续读」这个数字从 j 改成了 k。而这一步改动之所以可能，是因为 Transformer 里一个 token 算完之后，对外留下的只有 K 和 V，hidden state 并不交给后面的 token。信息要传下去，物理上只有 K/V 这一种载法。

所以 G 的定义也就顺理成章：把 item 文本和 k 个 gist token 拼起来前向一遍，取出 gist 位置每一层的 key 和 value。它实际上是 L 个层各一份 K/V——当成「一个向量」来想会出错。

这里值得停下来问一句：为什么不干脆用双塔（bi-encoder），把 item 压成一个 pooled 向量？原因在交互的粒度。单向量在线只能算内积，query 与 item 之间除了一个标量之外没有别的通路；gist 给的是 k 个位置的 KV，query 仍然能对这 k 个位置做真正的注意力，字段级的细粒度匹配得以保留。全量交叉编码器（cross-encoder）的交互最全，但每个 query 都要重跑长 item，不可预计算。gist 恰好卡在两者之间：item 侧的二次开销只在离线付一次，在线只剩 query 自己的部分加一段短前缀。

压哪一侧

既然要压，先问压哪一侧。一条请求里，一条 query 配 N 条候选；一条 item 在它的生命周期里被 M 条 query 打过。两侧的复用都成立，但收益差得远。不压缩时每条候选要过 j + ℓ 个 token 的层，只压 item 的话每条候选只剩 ℓ 个 token，只压 query 的话每条候选仍要过 j 个。由于 j 远大于 ℓ，后者的在线开销几乎等于不压。

放到总量上看，差距更大：item 侧的节省是 M × j，query 侧是 N × ℓ，而 M 与 N 差着几个数量级、j 与 ℓ 又差一个数量级。所以压 item 是显然的。这个判断在论文里恰好反过来，它压的是指令，因为指令被反复引用；而在我们这里，被反复引用的那一侧是 item。

训练改什么

训练只需要改掩码：gist 之后的 token 不能看 gist 之前的 token，形状上是普通因果掩码挖掉左下角那一块，论文说大约十行代码。item 看不见 query，query 也只能通过那 k 个位置看见 item；这个瓶颈由结构强制产生，不靠 loss 项施压。损失照常算，梯度只能穿过 gist 回流到对 item 的编码上。想预测得准，模型就得把 item 里真正有用的东西压进那 k 个位置。

以下是两种形态：

训练时 item 必须在场，gist 靠读它才学得会压缩；推理时 item 的位置整个消失，gist 已经在缓存里。这个不对称是整套方案的核心，也是最容易在实现里搞混的地方。把推理的写法顺手搬到训练，等于教模型压缩空气。

一次 attention 的实际形状

在线时序列里没有 item，也没有 gist 占位符。token 层面只有 query，gist 是以 KV 的形式在注意力里出现的。

两处值得说。第一，第 i 层的 G 依赖 item 跑完前 i−1 层的隐状态，所以离线必须把 item 完整跑一遍全层，逐层把 gist 位置的 K/V 都存下来，存储量是 2 × L × k × n_kv × d_h 每一条，而不是一个向量。

第二，位置编码。训练时 gist 在 j+1 到 j+k，query 在 j+k+1 之后；推理时把 query 从 k+1 起编，两边 query 到 gist 的相对距离都是 k。RoPE 只依赖差值，整体平移不影响点积，所以这个编号方式在数学上是等价的。但若框架按序列长度自动生成 position_ids，你把 j 个 token 删掉之后 query 就从 1 起编，相对距离变成负的或者别的什么，注意力全错，而且不报错，只是指标莫名掉一截。这是这类实现里最难查的一类 bug。

论文对这一点全篇没有交代，只在第六节顺口提了一句绝对位置编码会限制窗口，没有任何实验——这一段没有现成答案，只能自己试。

顺带说一个更容易踩的坑。既然 item 的位置在推理时被掩码挡住，会有人想：干脆把它们填零、留在序列里，反正不参与计算。这个等价性有一个很硬的前提，就是 gist 的 KV 必须真的来自缓存。若框架没有 prefix cache 的注入路径，「填零」就变成让 gist 对着一堆零做注意力，压出一个空表示，输出完全错。更要命的是它一点开销都省不下来：填零的 token 仍然占着位置，仍然要做 QKV 投影、仍然要逐层跑 FFN。要省的是把 j 从序列里拿掉，而不是留着它占位。

算力的开销

这是最容易被误读的地方。

每层每 token 的 MAC 数，线性部分大致是：QKV 投影（GQA 4:1）1.5d²，输出投影 d²，MLP 8d²，合计 10.5d²。注意力部分，对 S 个可见 key 打分再加权，是 2Sd。两者相除，d 约掉一项：

代入 d = 896、S = 72（k = 8、ℓ = 64），得到 1.5%。序列长度只通过 2Sd 这一项进来，而它在总量里始终是个零头。

换成论文附录 F 的说法更清楚：每层注意力里只有三个算子依赖 KV 长度（KQ logits、softmax、softmax 乘 V）；单个新 token 的 QKV 投影和整个 FFN 与 KV 长度无关。

以下是这个比例的走势：

注意力要到 S ≈ 5d 才能与线性部分打平，d = 896 时是 4700 个 token 左右，短序列下它永远追不上。这顺便解释了长上下文之所以贵的原因：S 一涨，它就无上限地涨，而线性部分纹丝不动。

拿这个结论回头读论文摘要，会读出一点别的味道。摘要说 40% 的 FLOPs 下降，那是对着完全不缓存算的。把对手换成指令 KV 缓存，同样是一行配置，收益是 0.11%，墙钟 1.0%。26 压到 1 的理论上限就是 0.12%，实测 0.11%，一分不多。

墙钟降 1.0%，比 FLOPs 的 0.11% 高出一个数量级，原因是这个规模下瓶颈在 HBM 搬运——那 1% 里真正省下来的不是算力，是 KV 读取。

顺着这条线把剩下的成本补齐。decode 是带宽瓶颈，不是算力瓶颈：一步里每个候选摊到的权重是 810 KB（24 层 × 16.9 MB，批 500），KV 是 192 KiB，约占五分之一；批到两千左右两者持平。所以「砍 k 不省算力」这句只对 FLOPs 成立，在线延迟恰恰由 KV 读取这条流量决定。

顺带说一句，如果目标只是「在同样的机器上跑更大的模型」，gist 这个量级买不动它。真正的数量级杠杆在别处：MoE 稀疏、KV 量化（KV quantization），以及投机解码（speculative decoding）这类手段，随便一个都是成倍的收益。gist 的独特性在于它不需要改架构。模型冻结、结构动不得的生产环境，改改掩码就能拿到一部分收益，这是别的手段给不了的。

存储的开销

公式是 2 × L × n_kv × d_h × b。麻烦在于同一档位的模型，KV 头部配置差得很远。同样 k = 8、10 万条 item、fp16：

  • 24 层、2 个 KV 头、head_dim 64：每位置 12 KiB，总量 9.2 GiB
  • 32 层、5 个 KV 头、head_dim 64：每位置 40 KiB，总量 30 GiB
  • 28 层、8 个 KV 头、head_dim 128：每位置 112 KiB，总量 85 GiB

配置不同，总量可以差到九倍。所以「一张 80G 卡能装 10 万条」这种话没有意义，得代入实际配置——第三格那一档，一张 80G 卡连 10 万条都装不下。

GQA 在这里是双刃。它让 G 按 KV 头数存，本身就省；可每层每个 gist 位置只提供 n_kv 组 V，要供 n_h 个 query 头共用。64 个 query 头配 8 个 KV 头，通道就窄了八倍。存储省下来了，用来承载细节的容量同时变窄。论文只用了 MHA 的 LLaMA-7B，没碰过这个维度。

按 item 分片

装不下就分片，但分片要连计算一起切，不能只切缓存。

因为一次打分里，query 侧要传的只是 token id，ℓ = 64 也就二百多字节，item 侧则是 96 KiB，差两个数量级。所以该让 query 去 item 那边算；反过来把 G 拉到 query 这边算，一次请求就要传几十 MB。

一条请求 50 条候选，按 item id 哈希到 M 片，每片分到 50/M 条，算完回传几个分数。这里有两层扩容：分片扩容量，复制扩吞吐，总机器数是两者之积。缓存是可从 item 内容重算出来的，不是有状态数据，所以分片不必为可用性做副本。某片挂了，那部分 item 退回现场重算，慢一些但不影响正确性。

按第一格的配置算，1000 万条 item 是 916 GiB，一张 80G 卡留 70 GiB 给缓存，M ≈ 14；换成第三格，M ≈ 122。同一份需求，八倍的机器差——全在 KV 头数上。

再进一步

item 压完，很自然会问 query 能不能也压。形状是：query 也压成 k′ 个 gist 位置，在线只剩 EOS 一个 token，对 k + k′ 个 key 做注意力。

算力上的收益漂亮得不像话。ℓ = 64、N = 50，token-层单位从 50 × 64 降到 64 + 50 × 1，二十几倍。而且算 query gist 的一次性成本大致等于今天一条候选的成本（都是 ℓ 个 token 过 L 层），所以 N ≥ 2 就抵得过来。论文那边给出的复用门槛也是 R = 2，两边算的是同一件事。

代价落在另一处。query gist 是在见到 item 之前就定死的。交叉编码器的核心能力，恰恰是 query 能按 item 重新解读：同一句「大号红色卫衣」，对着不同候选，该被激活的是不同的词。只压 item 时这个能力还在，ℓ 个 query token 各对着 G 做一次注意力，等于对 item 有 ℓ 个视角，最后在 EOS 汇合。query 也压掉之后，只剩一个视角。

这种形态在服务端反而更干净。

两个块都是只读的，没有任何 token 会往它们后面追加，所以零复制、零写放大。EOS 那一个 token 的 KV 根本不用写，因为后面没有 token 会来读它。整条路径退化成一次无状态的前向：读两个只读块，算一个 token，出分。

麻烦在于不能用 hash-based prefix cache。item 的 G 没有对应的 token 前缀，它是离线算出来的，跟任何输入序列都不对应，必须走显式的 KV 注入，或者自己写一层 attention 把预计算块拼进去。这属于实打实的开发量，不是开个开关就有。另外把 k + k′ 对齐到块大小（vLLM 是 16）是免费的优化，8 + 8 正好一块；不对齐就是四分之一的浪费。

真正决定成败的东西

前面都是工程上的成本。真正的问题在效果，而且是一处错配。

论文的成功模式是「意思对、格式错」。它举的例子是：指令要求从 News & Buzz、Travel、Style、Arts & Culture、Politics 里选一个分类，正控答 Arts & Culture，gist 答 Culture。语义没错，枚举值错了。Human 集上逐字一致率只有约 10%，而模型还能拿到 45.8% 的胜率，它就是靠着意思对活下来的。

相关性判定不吃这一套。它是判别任务，判的恰恰是逐字级字段是否匹配：型号、容量、年份。「iPhone 15 Pro 256GB」和「128GB」的差别，正是被压掉的那一类信息。论文的强项是语义近似，我们的需求是字段精确，两者正交，调参解决不了。

论文那句「k 不敏感，k = 10 反而更差」也不能直接搬。它成立的前提是信息余量极大：26 个离散 token 大概几百 bit，塞进 26 万个浮点数，k = 1 已经富余得离谱。我们这里是 j ≈ 1000 压到 k，压缩比高一个数量级，这个前提直接不成立。论文自己把「压缩很长的 prompt、大 k 的少样本」列进了未来方向，明说没做。

还有一个反向的警告。论文里 TF-IDF 那组对照在 FLAN-T5 的 Human 集上拿了 −5.9，比完全不压还差。压得不够解释不了这个数；它压错了方向，留下一个显眼但无关的关键词，反而误导。gist 若压掉的是规格字段、留下的是营销词，结局一样。

顺便把评估口径钉死。级联里最危险的是承接率掉：item 压过之后某些候选被打低，进不了下一阶段，后面的模型再好也救不回来。所以该量的是它对全量排序 oracle 的 recall@K——拿不压 query 时的全量排序当参考答案，看这一档的 top-K 捞回了多少。这个数掉得多，说明这一档不该待在这个位置，得把 k 加大或者干脆退回全量。

所以顺序应当反过来。先把「item 压、query 留原样」这一档跑通，k 从 4 扫到 16，评估按 j 的分位切开看。长 item 承担了几乎全部损失，只看全局平均会把它们稀释掉。

query 留原样，保住的正是字段级对齐这个能力。两边都压的算力收益更漂亮，但它关掉的东西，恰好是相关性判定最需要的那样东西。
